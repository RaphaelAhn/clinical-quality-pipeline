# 설계와 데이터 계약

## 목표

서로 다른 기관의 합성 진료 CSV를 일별 스냅샷으로 정리한다. 입력이 잘못되거나
적재 중 실패했을 때 소비자에게 불완전한 결과를 노출하지 않는 것이 핵심이다.
실제 환자 데이터 처리, 의료 판단, 운영 서비스 및 완전한 OMOP 변환은 범위 밖이다.

## 데이터 흐름

```text
hospital_A.csv (YYYY-MM-DD, mg/dL) ─┐
                                  ├─ 파일/헤더 계약 → 필드 검증 → 기관별 토큰화
hospital_B.csv (YYYY/MM/DD, mmol/L) ┘                     │
                             잘못된 행 → 행 위치·오류 코드 격리
                                                        │
                                      임시 stage → 중복 제거·충돌 검사
                                                        │
                    BEGIN → 해당 날짜 교체 → 관계·건수 검사 → COMMIT
                                       실패 → ROLLBACK
                                                        │
                               세 스냅샷 테이블 + runs 실행 기록
```

## 입력 계약

- 두 파일 모두 필요하며 헤더는 `clinical_pipeline.COLUMNS`와 순서까지 같아야 한다.
- 한 행은 환자·방문·검사 정보가 결합된 합성 검사 이벤트다. 기관당 하나 이상의 정상 행이 필요하다.
- `patient_id`, `visit_id`, `measurement_id`는 각각 `SYN-P-숫자`, `SYN-V-숫자`, `SYN-M-숫자`이다.
- 검사 코드는 가상의 `DEMO_GLU`만 허용한다. 임상 코드·표준 용어집 매핑이 아니다.
- 날짜는 기관별 명시 형식만 허용하고 실재 날짜인지 검사한다. 방문일·검사일은 요청 배치일과 같아야 한다.
- 이 데모는 당일 방문·당일 검사만 다룬다. 입원 기간, 방문 없는 검사, 다일 방문은 지원하지 않는다.
- 출생연도 1900~배치 연도, 숫자 0~10,000은 합성 입력 계약이다. 정상/비정상 임상 판정 범위가 아니다.
- 예시 단위 변환은 `mmol/L × 18 → mg/dL`, 소수점 넷째 자리 반올림이다.
  물질별 일반 변환기나 임상적으로 검증된 계산기가 아니다.
- 한 날짜의 두 기관 **전체 스냅샷**만 받는다. 증분 파일만 넣으면 빠진 레코드가 삭제되므로 허용하지 않는다.
- 기관마다 송신 측 행 수 파일 `hospital_X.rows`가 필요하다. 읽은 행 수가 다르면 배치를 차단한다(`SOURCE_ROW_COUNT_MISMATCH`).
  깨끗하게 파싱되지만 잘린 파일은 다른 검사로 드러나지 않는다(Embulk 덮어쓰기 사례). 파일과 행 수가 함께 조작되는 경우는 막지 못한다.

## 품질 판단

| 조건 | 동작 |
|---|---|
| 누락, 잘못된 날짜/단위/코드/수치 | 해당 행을 제외하고 위치·이유 기록 |
| 제외 비율 > 10% | 배치 전체 차단, 기존 데이터 유지 |
| 완전히 같은 행 재전송 | DISTINCT로 한 번만 저장, 중복 건수 별도 기록 |
| 같은 검사 키인데 다른 내용 | 임의의 최신값 선택 없이 배치 차단 |
| 같은 환자의 출생연도 충돌 | 배치 차단 |
| 같은 방문이 다른 환자에 연결 | 배치 차단 |
| 기관 파일 누락, 빈 배치, 정상 행 없는 기관 | 배치 차단 |
| 작업 사이 또는 읽기 전후 파일 체크섬 변경 | 배치 차단 |
| 적재 후 참조 누락·건수 불일치 | 트랜잭션 취소 |

10%는 검증 시연을 위한 정책값이다. 실제 병원 데이터 품질 허용 기준이 아니다.
관계 검증은 이 평탄화된 입력에서 만든 테이블 간 일관성만 확인하며 실제 EMR 참조를 검증하지 않는다.

## 왜 DuckDB와 원자적 교체인가

SQL로 중복·충돌·참조·건수를 검사하고 파일형 DB로 재현할 수 있어 선택했다.
세 테이블과 COMMITTED 실행 기록을 하나의 트랜잭션으로 갱신한다.
삭제 직후 또는 삽입 직후 장애를 주입하면 기존 스냅샷이 복구되는지 해시로 비교한다.
별도의 FAILED 기록은 롤백 뒤 남기므로 실패 시도와 성공 상태를 구분할 수 있다.
프로세스 강제 종료 시 FAILED 기록이 없을 수 있다. 이 경우 커밋 여부는 DB 상태로 확인해야 한다.

단일 작성자 모델이다. Airflow의 max_active_runs=1은 같은 DAG 실행만 직렬화하며,
다른 프로세스나 별도 DAG까지 통제하지 않는다. DB 동시 작성은 운영 설계 범위 밖이다.
파일 체크섬 전후 비교는 단순한 변경을 탐지하지만 읽는 중 변경 후 원복되는 상황까지 차단하지 않는다.
운영형 입력에는 불변 객체나 스냅샷 전달이 필요하다.

## 두 엔진과 동등성

- `engine="python"`(기준): csv 모듈로 읽고 행마다 `normalize()`. 정규화한 행은 1,000행씩 타입 지정 JSON으로 stage에 넣는다.
- `engine="sql"`(기본): DuckDB `read_csv`로 읽고, **엄격한 ASCII 조건**(ID 정규식, 날짜 형식+실재 날짜=배치일,
  출생연도, 코드·단위, 소수 4자리 이하 값)을 통과한 행만 SQL로 변환한다. 이 조건은 `normalize()`가 받아들이는 입력의
  부분집합이고 같은 값을 만든다. 나머지 행은 전부 `normalize()`로 보낸다. 그래서 격리 사유·결과가 구조적으로 같다.
- 행 번호를 믿을 수 없는 파일(빈 줄, 따옴표 안 줄바꿈, 열 개수 오류)은 파일 전체를 Python 엔진으로 처리한다.
- HMAC 토큰은 SQL 매크로 `sha256(K^opad || sha256(K^ipad || msg))`로 계산한다. 빠른 경로 ID는 JSON 이스케이프가
  생길 수 없어 `token()`과 바이트 단위로 같다.
- 결과 해시(`snapshot_sha256`)는 DuckDB에서 행별 sha256을 정렬해 이어 붙인 뒤 다시 해시한다. 순서와 무관하다.
- 동등성은 `test_sql_engine_matches_reference_python_engine`(공백·전각 숫자·지수 표기·빈 줄 등 6개 시나리오)이 확인한다.

## 개인정보 관련 경계

원천 식별자는 기관+엔티티 종류를 포함한 HMAC-SHA256 토큰으로 바꾼다.
기관 간 동일 식별자가 같은 사람이라는 추정을 하지 않는다. 이름·전화·주소·자유 텍스트 열은 받지 않는다.
격리/실행 기록에는 원문 대신 파일 구분·행 번호·고정 오류 코드만 남긴다.
DB에 키 버전 식별값을 고정해 키가 달라진 채 같은 DB에 쓰는 것을 차단한다.

**공개된 데모 키를 사용하므로 실제 비밀키 보호나 익명화가 아니다.**
날짜·출생연도도 남아 있다. 원천 CSV는 토큰화 전 합성 ID를 보유하며 자동 파기하지 않는다.
실제 데이터 도입, 법적 비식별 적정성, 재식별 위험 평가를 수행하지 않았다.

## OMOP 범위

OMOP-CDM의 person–visit_occurrence–measurement 관계를 학습 대상으로 삼았지만,
이 구현은 날짜별 snapshot 구조와 문자열 토큰을 사용하는 **독자 스키마**다.
정식 테이블명, 필수 필드, 정수 키, concept/vocabulary 매핑, 관찰기간 등을 갖추지 않았다.
따라서 OMOP 호환·인증·표준화 완료로 표현하지 않는다.
