# 의료 도메인 메모: OMOP 매핑과 가명처리

이 프로젝트의 독자 스키마가 OMOP-CDM 5.4와 개인정보보호법의 어느 부분에 닿아 있고, 어디가 비어 있는지 정리한다.
법률 자문이 아니며, 조문은 번호·제목만 법령정보센터에서 확인했고 내용은 요약이다. 실제 적용 판단은 원문과 가이드라인으로 한다.

## 1. OMOP-CDM 5.4 매핑 (MEASUREMENT 중심)

컬럼 정의 출처: [OHDSI CDM 5.4](https://ohdsi.github.io/CommonDataModel/cdm54.html). ★ = CDM 필수 컬럼.

| CDM 컬럼 | 이 프로젝트 | 상태 |
|---|---|---|
| ★ measurement_id | `measurement_id` (기관별 HMAC 토큰, 문자열) | 🔶 CDM은 정수 키. 토큰→정수 대리키 테이블 필요 |
| ★ person_id | `person_id` 토큰 | 🔶 동일 |
| ★ measurement_concept_id | 없음. 원천 코드 `DEMO_GLU`는 가상 코드 | ❌ 원천 코드 → 표준 개념(예: LOINC 혈당 검사) 매핑 필요. 매핑 전에는 0 |
| ★ measurement_date | `measurement_date` | ✅ |
| ★ measurement_type_concept_id | 없음 | ❌ 출처 유형(EHR 등) 개념 필요 |
| value_as_number | `value` (mg/dL로 변환된 값) | ✅ |
| unit_concept_id | 없음 | ❌ mg/dL 단위 개념 매핑 필요. CDM 규칙상 단위는 있는데 매핑이 없으면 0 |
| visit_occurrence_id | `visit_id` 토큰 | 🔶 정수 키 문제 동일 |
| measurement_source_value | 보존 안 함 | ❌ CDM은 원천 코드 원문(`DEMO_GLU`) 보존을 권장. 추가 필요 |
| unit_source_value | 보존 안 함 (변환 후 `mg/dL`만 남김) | ❌ 원천 단위(`mmol/L`)를 남겨야 변환 추적 가능 |
| value_source_value | 보존 안 함 | ❌ 원천 값 원문 보존 필요 |

PERSON은 `year_of_birth`(★)만 있고 `gender_concept_id`·`race_concept_id`·`ethnicity_concept_id`(★)가 없다.
VISIT_OCCURRENCE는 `visit_start_date`만 있고 `visit_concept_id`·`visit_end_date`·`visit_type_concept_id`(★)가 없다.

**배운 점**: 지금 설계는 "변환 후 값만 남기는" 방식이라, CDM이 요구하는 *원천값 보존(source_value)*과 어긋난다.
정식 CDM으로 옮긴다면 ① 원천 코드·단위·값 원문 보존 ② source_to_concept 매핑 테이블(버전 고정)
③ 매핑 안 된 코드는 0으로 두고 매핑률을 품질 지표로 기록 ④ 토큰→정수 대리키 발급 순서로 진행한다.

## 2. 개인정보보호법과 이 프로젝트의 가명처리

| 조문 (번호·제목 확인) | 요지 (요약) | 이 프로젝트 | 빈 곳 |
|---|---|---|---|
| 제2조 1의2 가명처리 | 추가 정보 없이는 특정 개인을 알아볼 수 없게 처리 | 환자·방문·검사 ID를 HMAC 토큰으로 대체. 키 = 추가 정보 | 데모 키가 코드에 공개돼 있음 → 실제로는 가명처리가 아님 |
| 제23조 민감정보 | 건강 정보는 민감정보로 더 엄격하게 다룸 | 이름·연락처·자유 텍스트 열을 받지 않음. 격리 기록에 원문 값 미기록 | 검사값·날짜는 그대로 남음 |
| 제28조의2 가명정보의 처리 등 | 통계·과학적 연구 등 목적의 가명정보 처리 | 연구용 RWD 구축이 이 조문의 목적 범위에 해당 | 목적·처리 기록 관리 없음 |
| 제28조의3 가명정보의 결합 제한 | 서로 다른 처리자의 가명정보 결합은 지정 기관을 통해서만 | 토큰에 기관을 넣어 **기관 간 같은 ID가 같은 토큰이 되지 않게** 함 → 파이프라인이 임의 결합을 하지 않음 | — |
| 제28조의4 안전조치의무 | 추가 정보를 분리 보관하고 접근을 통제 | DB에 키 **버전 식별값**만 저장, 키가 바뀐 채 쓰기 차단(`KEY_VERSION_MISMATCH`) | 키 분리 보관(비밀 관리 도구·권한 분리) 미구현 |
| 제28조의5 금지의무 | 특정 개인을 알아보려는 처리 금지 | GX 감사가 스냅샷에 원본 ID(`SYN-*`)가 새어 나오면 실패 처리 | 재식별 위험 평가(출생연도+날짜+기관 조합) 미수행 |

**남는 위험 한 가지**: 출생연도·검사일·기관·검사값 조합은 소수 인원에게는 식별 단서가 될 수 있다.
실제 데이터였다면 k-익명성 같은 재식별 위험 평가와 날짜 이동·범주화 같은 추가 처리를 검토해야 한다.

## 3. 다기관 연구 플랫폼 맥락에서 이 구조의 의미

분산형 다기관 연구 플랫폼은 데이터를 병원 안에 두고 분석·학습을 분산시키는 모델이다.
이 프로젝트의 "기관별 네임스페이스 토큰 + 기관 간 임의 결합 금지"는 같은 방향의 작은 연습이며,
실제로는 병원마다 비밀키·매핑표·품질 기준을 두고 결과(집계·모델)만 밖으로 보내는 구조가 된다.
